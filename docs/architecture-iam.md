# Butler 在智能体授权体系里的位置

**一句话：权限检查回答"能不能读这份"，Butler 补上"你累计拿到的东西，能不能拼出你不该知道的结论"。** 这是同一类问题——单次合法、多步累积越界——在数据面的实现。

下文把 Butler 对应到一个常见的智能体授权控制平面（身份登记 → 凭证获取 → 策略决策 → 调用执行 → 审计回收）。这个框架来自我们旁听的一次技术分享，**我们没有参与那个项目，也没有接入它的任何组件**；这里只是借它的分段来讲清楚 Butler 管哪一段、不管哪一段。

## 概览图

```
                 ┌───────────── 身份登记 ─────────────┐
 用户/来源系统 ──▶ 成员、角色、组；来源 ACL 同步（撤权在一次同步后生效，演示里约几十毫秒）
                 └────────────────┬──────────────────┘
                                  ▼
                 ┌───────────── 凭证获取 ─────────────┐
                 │ 账号密码 / OIDC；内部服务凭据        │   ← 现状：登录凭证，非任务级凭证
                 └────────────────┬──────────────────┘
                                  ▼
 提问 ──▶ 检索（只取有权读的文档）
                                  ▼
                 ┌───────────── 策略决策 ─────────────┐
                 │ ① 文档级 ACL（能不能读这份）          │
                 │ ② 会话账本：本会话已放行了什么        │   ← 状态约束
                 │ ③ 依赖闭包：登记的前提是否凑齐        │   ← 累积越界
                 │ ④ 结论判官：回答是否说出/暗示受限结论  │
                 │ ⑤ 预授权：被批准的结论放行，其余照拦   │   ← 审批疲劳
                 └────────────────┬──────────────────┘
                                  ▼
                 ┌───────────── 调用执行 ─────────────┐
                 │ 生成（看不到无权文档）→ 引用核验 →    │
                 │ 放行 / 降级 / 需要授权               │
                 └────────────────┬──────────────────┘
                                  ▼
                 ┌───────────── 审计回收 ─────────────┐
                 │ 哈希链 + 签名检查点 + 独立验证工具     │
                 │ 记录：申请、批准人、有效期、被拦结论编号│
                 └────────────────────────────────────┘
```

## 对应关系

| 智能体授权里的要求 | Butler 里的做法 | 状态 |
| --- | --- | --- |
| 认证成功 ≠ 有资源权限 | 登录后每次提问仍按文档 ACL 过滤检索结果，生成器看不到无权文档（有断言守着） | 已实现 |
| 有资源权限 ≠ 本次操作合理 | 文档都有权看，但累计拿到的资料凑齐某条受限结论的依据时，不再放行 | 已实现（核心贡献） |
| 多步累积越界，要有历史会话感知 | 会话账本记录已放行内容；每轮把"历史已放行 + 新草稿"一起检查，不是只查这一轮 | 已实现 |
| 预授权区间，缓解审批疲劳 | 被拦时转成"需要授权"而不是死拒答；管理员批准后在有效期内放行，到期自动失效；只有凑齐结论的那一步才需要批 | **本轮新增**，已测试 |
| 关键变更需确认；不能自己批自己 | 审批人不能批自己的申请；申请里只存结论编号和问题哈希，申请人看不到是哪条结论 | 已实现 |
| 审计可回收、策略引擎自身要防越权 | 哈希链审计 + 签名检查点，独立工具验证，改一条记录就失败；批准动作本身也写进审计 | 已实现（审批人账号本身的防护依赖部署的身份系统） |
| 撤权要立刻生效 | 来源系统改权限，同步后文档级权限立即重新判定，旧会话作废 | 已实现；但管理员批准的预授权记录不会因来源撤权自动作废，只靠到期（已知缺口，文档级 ACL 仍照常生效） |

## 明确不做、或还没做的

- **不管工具调用面。** Butler 拦的是"回答里的结论"，不拦 agent 去调用工具、写文件、发请求。Cedar / OpenFGA 这类外部策略引擎挂在工具调用前置点上的方案，我们没有做。
- **没有区分应用 / Agent / 运行实例 / 任务上下文。** 现在的主体只有"用户 + 会话"。多 Agent 委托、主子 Agent 权限动态收缩都没有。
- **凭证是登录凭证，不是按任务签发的短期凭证。**
- **结论要先登记才能走依赖闭包**（或由系统自动发现前提）；没登记的结论只能靠 LLM 判官，判官有漏拦也有过拦（见 [独立评测](independent-eval.md) 与 [抽样复核](human-review.md)）。
- 审批界面只有 API（`/workspace/approvals`），前端还没有审批页面。

## 为什么这样切

数据面与工具调用面的共同点是"状态"：单次检查看不出来的越界，只有带着历史才看得出来。Butler 用会话账本 + 依赖闭包解决数据面；工具调用面可以用同样的思路（调用序列账本 + 外部策略引擎），但那是另一个组件，不在这次交付里。
